# 项目整理

通用的项目结构扫描与整理工具，适用于任意语言和框架的项目。

## 触发场景

- 项目文件杂乱，需要重新组织目录结构
- 存在冗余、重复、过时的文件需要清理
- 命名风格不统一，需要规范化
- 新接手项目，需要梳理结构
- 项目膨胀，需要瘦身优化

## 整理流程

### 第一步：扫描项目概况

1. 使用 `Glob` 和 `Shell`（tree / ls）获取项目整体结构
2. 识别项目类型（语言、框架、构建工具）
3. 统计文件数量和大小分布
4. 识别配置文件、依赖管理文件、入口文件

输出项目概况摘要：

```
## 项目概况
- 语言/框架：[识别结果]
- 文件总数：[数量]
- 主要目录：[列表]
- 构建工具：[识别结果]
```

### 第二步：识别问题

逐项检查以下常见问题：

| 问题类别 | 检查内容 |
|---------|---------|
| 冗余文件 | 临时文件、编辑器备份、OS 生成文件、构建产物 |
| 缺失配置 | .gitignore、.editorconfig、README、LICENSE |
| 命名不规范 | 大小写混用、空格/特殊字符、命名风格不统一 |
| 目录混乱 | 源码与资源混放、测试文件散落、无明确分层 |
| 依赖问题 | 未锁定版本、冗余依赖、本地路径依赖 |
| 大文件 | 二进制文件入库、日志文件未忽略、数据文件混入源码 |

### 第三步：生成整理方案

按优先级输出整理建议：

**P0 - 必须处理**：影响项目运行或协作的问题
**P1 - 建议处理**：影响可维护性的问题
**P2 - 可选优化**：锦上添花的改进

对每个建议给出：
- 问题描述
- 具体操作（移动/删除/重命名/新建）
- 影响范围评估

### 第四步：执行整理

使用 `ask_question` 向用户确认方案后再执行。

执行时按以下顺序操作：
1. **先备份**：对高风险操作先提醒用户备份
2. **先移动后删除**：优先归类，确认无误再清理
3. **逐步执行**：每步操作后用 `send_progress` 报告进度
4. **验证结果**：操作完成后重新扫描，确认结构符合预期

## 常见项目结构参考

### 通用项目

```
project/
├── src/              # 源码
├── tests/            # 测试
├── docs/             # 文档
├── scripts/          # 脚本工具
├── assets/           # 静态资源
├── config/           # 配置文件
├── .gitignore
├── README.md
└── [构建/依赖配置]
```

### 不同项目类型的典型约定

根据识别的项目类型，参考对应语言/框架的社区最佳实践来建议目录结构。不强制套用模板，尊重项目已有的合理组织方式。

## 命名规范参考

| 类型 | 推荐风格 | 示例 |
|------|---------|------|
| 目录 | kebab-case 或 snake_case | `my-module/`、`my_module/` |
| 源码文件 | 跟随语言惯例 | Python: `snake_case.py`、JS: `camelCase.js` |
| 配置文件 | 跟随工具惯例 | `.eslintrc.js`、`tsconfig.json` |
| 文档 | UPPER 或 Title | `README.md`、`CHANGELOG.md` |

## 原则

1. **安全第一**：任何删除或重命名操作前必须确认，高风险操作提醒备份
2. **尊重现有结构**：不为"规范"而强改运行良好的项目，只修问题不搞强迫症
3. **渐进式整理**：大项目分批整理，每批确认后再继续
4. **保持可运行**：整理后确保项目仍能正常构建和运行
5. **记录变更**：整理完成后输出变更清单，方便回溯
